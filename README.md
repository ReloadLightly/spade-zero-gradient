# spade-zero-gradient

Can SPADE's Environment Designer improve **without weight updates**?

[SPADE](https://arxiv.org/abs/2608.19197) (Liu, Yu et al. 2026, UW/Jaques
group) trains a single LLM to both write executable Gym-style training
environments and solve them, rewarding the designer with *hint-based regret* —
the solver's return with a privileged hint minus without — optimized by RL.
Its Future Directions leave one question open:

> "Future work could explore Environment Designers that improve through
> in-context learning rather than gradient updates."

This repo answers exactly that, at small scale, with frozen models only:

- **Designer** (Sonnet, frozen) improves only through (a) an accumulated
  in-context **environment memory** and (b) **ShinkaEvolve-style evolution of
  its written design strategy**, selected on floored hint-based regret.
- **Solver** (Haiku, frozen) removes SPADE's co-evolution confound: any
  fitness trend is attributable to the designer side.
- Conditions: **C0** static designer · **C1** memory only · **C2**
  memory + strategy evolution. Fitness and gates are pre-registered in
  [PREREG.md](PREREG.md); all outcomes (including null) are reportable.

## Layout

    szg/            harness: env contract & sandbox, runner, gates, memory,
                    designer, evolution, fitness, CLI
    strategies/     S0 baseline designer strategy (control + evolution seed)
    seeds/          fixed topic grounding pack (60 topics, 3 skills)
    tests/          acceptance tests pinning the package API (no model calls)
    runs/           JSONL logs (envs, episodes with transcripts, rounds)
    PREREG.md       frozen design: fitness, gates, endpoints, decision log
    CLAUDE.md       stage plan for Claude Code main runs (subscription-backed
                    headless `claude -p`, no API key)

## Quickstart

    pip install -e . && pip install pytest
    make test     # acceptance tests, no model calls
    make smoke    # machinery gates R4/R5, no model calls
    make gates    # R1-R3 real-model probe (claude CLI) — STOP gate
    python -m szg.cli round --condition C2 --round-index 0 --n-envs 6 \
        --mutate --out runs/c2_chain0

### How to read the numbers above

The trajectory table is **live experimental data, not a result.** Four
independent problems currently sit between it and any claim, all logged as
they were found:

1. **The comparison is underpowered.** C0 is a static control — frozen S0, no
   memory, nothing accumulating — so its rounds are repeated draws of one
   fixed process. Those draws span the full range of fitness observed
   anywhere in the grid (sd ≈ 0.09, against fitness levels of ≈ 0.1). The
   registered endpoint (PREREG §5) averages the final third, i.e. 2 rounds
   per condition, which cannot resolve an effect at that noise level.

2. **C2 has rarely run an evolved strategy.** Strategy selection is
   ε-greedy at ε = 0.25, so an untried child is picked only a quarter of the
   time while `--mutate` adds one child per round. Simulated over a 6-round
   chain that is ~1.25 evolved rounds, with a ~24% chance of *none at all*
   and a ~56% chance that neither final-third round uses one. Rounds running
   S0 make C2 behaviourally identical to C1.

3. **A directional confound against C2.** Environments lost to designer-call
   timeouts fall almost entirely on C2 — the only condition whose prompt
   carries both a memory digest and an evolved strategy. It is penalised for
   holding more context, which is the mechanism under test. See
   [`runs/_findings/C2_designer_timeout_confound.md`](runs/_findings/C2_designer_timeout_confound.md).
   **C2 fitness should be read as a lower bound.**

4. **Fitness is close to a single-environment measurement.** In most rounds
   one environment supplies nearly all the regret. The best-composed round in
   the grid so far (6/6 valid, four positive-regret environments, difficulty
   squarely in band) scored the same as badly-composed rounds carried by one
   environment — composition quality and the registered metric are only
   loosely coupled.

Consequently, **if the primary endpoint returns NO_TRACTION it will not mean
"in-context design does not work"** — it will mean the instrument could not
see. The S4 writeup reports which registered outcome obtained *and* which of
these limits was binding. All four outcomes in PREREG §6 are equally
reportable and the run is not being steered toward any of them.
